What a Subagent Is

Prompt in, summary out, own context — that isolation is what lets us run a whole panel without filling the main conversation.
  • A subagent is a fresh, isolated Claude
  • The prompt you pass in is all it knows
  • Returns only a summary

01 · Parallel Swarms

Why Many Beats One

  • Ask one generalist to "review this" and you get a decent, shallow-but-wide pass
  • Ask a security person, a testing person, and a design person and you get three genuinely different sets of findings
  • Run them all at once, each blind to the others — that's a swarm. Two shapes do it, and we build one live.
It's a code-review board, or a panel of specialists reading the same contract. Not just for code.
The honest motivation
AI is a yes-man. A fresh subagent with a pointed lens gives you the critique the sycophant won't.

01 · Parallel Swarms

Two Shapes: Panel & Sweep

Panel same input, many lenses → resolves
varies: the lens  ·  this is what we build
scale with more viewpoints — copies just agree
Sweep many inputs, same job → aggregates
varies: the input  ·  my morning brief
scale with more searchers
Both are blind — and that's the point
Reviewers never see each other's work, so they can't converge — you keep the diversity you came for. It's structural, straight from the docs: "Subagents only report results back to the main agent and never talk to each other."

Start With a Prompt

From a blank file, prompt Claude to scaffold the skill. Keep v1 simple — no JSON, no preamble, no verdict yet — then improve it one prompt at a time. That's the rest of this section.
Create a skill called review-swarm that reviews the specified
file or files. Spin up three subagents in parallel — each
looks at a different thing, none see each other:

  security           — find the security holes
  test-quality       — do the tests actually assert anything?
  design-correctness — logic bugs the analyzer can't catch

Run them at once and report what each found.
All three run at once, so total time is the slowest subagent, not the sum — a serial loop would burn ~3× the wall-clock for the same findings.

02 · Build

Design the Subagents

Each subagent is a file — Claude writes it for you. Choosing the lens set is the real engineering judgment.
  • security — deterministic: drives sf code-analyzer run, triages the output
  • test-quality — reasoner: do the tests assert anything meaningful?
  • design-correctness — reasoner: business-logic bugs static rules can't see
  • Non-overlapping catch zones; genuine disagreement; mixed deterministic + probabilistic
The test to hand yourself
"If I removed this subagent, would I lose findings nobody else would catch?" If no, cut it.

02 · Build · v2

Split Into Agent Files

Give each subagent its own file under .claude/agents/ so I can
tune them separately — set each one's lens focus, model, and
tools, and lock them all read-only.
  • Each subagent becomes its own file — frontmatter sets model, effort, tools, disallowedTools
  • Match the model to the lens — a cheaper model on the shallow triage, a stronger one on the deep reasoner
  • Lock them read-only with disallowedTools — the analyzer gets Bash+Read; the reasoners get Read only
Say the principle out loud
Prompting "don't edit anything" is not a permission layer. If an agent can touch data, assume it will — read-only is a tool restriction, not an instruction.

02 · Build · v3

Give Them a Common Output

"Report what each found" gives three paragraphs you can't compare — a shared envelope turns three opinions into something you can sort, gate, and de-dupe.
▸ you type
Make every subagent return the same JSON: a verdict plus a
list of findings, each with severity, issue, and recommendation.
every subagent returns
{ "agent": "string",
  "verdict": "pass | warn | flag",
  "findings": [
    { "severity": "high | med | low",
      "issue": "string",
      "recommendation": "string" }
  ] }
Not a built-in
Subagents have no schema field. This is prompt instruction + your own validation in the parent — exactly right.
Have each subagent write its envelope to its own file, and tolerate nulls — if one dies or returns junk, the roll-up skips it instead of crashing.

02 · Build · v4

The Shared Preamble

Three bespoke prompts drift, and synthesis can't compare them — one preamble makes the N reviews commensurable.
▸ you type
They're all repeating the same setup — pull the common
instructions into one shared preamble, keep only each agent's
lens focus different, and tell each it's the only reviewer.
the preamble it writes
# One preamble, N focuses — and never tell an agent it has colleagues
You are the ONLY reviewer of {artifact}. Do not assume others exist.
Read it yourself. Focus ONLY on: {lens_focus}.
Return the shared JSON envelope — nothing else.
Why "no colleagues"
Tell an agent it's on a panel and it hedges — defers, softens. You lose the independence that was the point.

02 · Build · v5

Synthesize One Verdict

Synthesis is adjudication, not formatting — a swarm isn't done when the agents return; this is where N opinions become a decision.
▸ you type
After the subagents return, reconcile them into one verdict —
GO, CAUTION, or STOP — sorted by severity, and re-read the
source on any disagreement before ruling.
the logic it runs
# The orchestrator's job after the subagents return
verdict = any(flag) ? "STOP" : any(warn) ? "CAUTION" : "GO"
sort findings by severity (high -> low)
for any finding two agents dispute:
    RE-READ the cited lines before ruling      # not just collate summaries
output: one verdict + the ranked, de-duplicated findings

What We Kept: review-swarm

Everything v2–v5 accreted, in one file. Next time it's one command.
---
name: review-swarm
description: Review the specified file(s) with independent subagents,
  each a different lens, blind to the others, then synthesize one
  GO / CAUTION / STOP verdict. Use for Apex, a PR, a contract.
---
# Review Swarm
1. Take the target file(s).
2. Spawn every agent in .claude/agents/review-*.md in ONE message
   (parallel, read-only) — each gets the shared preamble + its lens.
3. Collect one JSON envelope per subagent.
4. Synthesize: gate to GO/CAUTION/STOP, sort by severity, RE-READ on conflict.
5. Return the verdict + ranked findings.

03 · When NOT to Swarm

Skip It When

  • The artifact is small — one strong checklist pass holds the whole thing
  • Cost or latency is the binding constraint — N agents is roughly N times the tokens
  • The concerns interact — one agent holding the whole picture reasons about tradeoffs better
  • Middle ground: one agent, sequential passes — ~1x cost, but loses independence
Say the quiet part out loud
This very demo is a "skip the swarm" case — a 40-line class you'd checklist in real life. I swarmed it so the machinery fits on screen. The pattern is the point, not this class.

04 · Trust It

Structure Is Not Accuracy

  • A schema makes results collatable, not true — three reviewers who each hallucinate confidently just give you three tidy hallucinations
  • So a separate agent grades the swarm's output — maker-checker, the plain name for adversarial verification
  • Make the check objective where you can ("fails WITH USER_MODE" is checkable, "risky" is not); where you can't, validate the verifier itself
A true story — prepping this talk
A subagent's fact-check came back confident and well-formatted — and partly fabricated, sourced to content farms dressed as docs. A skeptical second pass caught it. The twist: its biggest claim was actually true, just sourced from garbage. Verification is what tells you which half was real.

05 · Where It Goes

The Swarm Is One Rung

Everything so far was parallel and blind. Two shapes step outside that box — and the same idea also scales up.
  • Pipeline — agents as stages, each feeding the next. Sequential, not blind-parallel. Refines.
  • Debate — let reviewers see each other and argue. Trade independence for pressure-testing.
  • Nesting — a reviewer can itself fan out; subagents spawn subagents, up to 4 levels deep
  • Agent teams — teammates share a task list and talk to each other (experimental; "significantly more tokens")
  • Dynamic workflows — a script orchestrating agents at scale, triggered by ultracode (16 concurrent / 1,000 per run)
  • Bundled: /deep-research (web-search fan-out → cited report), /batch (per-unit worktrees → PRs)
  • And the swarm itself is a pattern, not a command — you define agents as files (/agents just points you there), run the pattern, and watch with /tasks
subagents → swarms → nesting → teams → workflows — the same idea turned up. Pipeline and debate are the same idea turned sideways.

Recap

The Whole Decision on One Slide

Swarm when
Large or complex artifact, distinct deep concerns, an expensive miss, each lens carries its own tools.
Don't when
Small artifact, cost/latency-bound, or the concerns interact. Checklist it, or one agent with sequential passes.
Which shape
Panel for many lenses on one thing, sweep for many things each covered once.
And whatever you build — verify it. Structure is not accuracy.
